> 这套"测量驱动"的叙事,是面试里区分"调包侠"和"RAG 工程师"的关键。

## 起点:先建评估,再优化

- 建了标注集(问题 → 应召回哪些 chunk)+ `npm run eval`(Recall@k / MRR)。
- 第一版语料只有 7 段,Recall@3=100%、MRR=1.0 —— **满分**。
- **关键判断:对着满分没法优化。** 于是先**扩语料到 22 段 + 加难标注集**(塞入易混淆对:三种"回收策略"、两种"访问模式"、三种"驱动"…),让指标掉下来、有下降空间,再开始优化。

## 逐个优化的真实结果(k=5)

| 模式 | Recall | MRR | 结论 |
|------|--------|-----|------|
| ① 无过滤基线 | 96.2% | 0.962 | 起点 |
| ② oracle 过滤(标注 resource) | 96.2% | 1.000 | 理想上限(作弊:用了标注) |
| ③ auto 关键词路由 | 96.2% | 0.962 | **净持平** |
| ④ rerank(粗召回+精排) | **100%** | **1.000** | **一锤定音** |

## 四个硬核教训

### 1. 元数据过滤的价值要在多个 k 下看
k=3 时 ② 看着没用(Recall 不动);k=5 时 ② 给了 +3.8pt。**别用单一设置给优化下结论。**
更深的价值藏在 top-k 列表里:基线"回收策略"查询的 top-5 有 **4 段是错资源的**(含写着"Recycle"的 pv-reclaim)——过滤后 5/5 同资源。**这是从源头掐掉"跨资源事实污染",降幻觉,Recall/MRR 有时看不出来。**

### 2. 关键词路由会翻车,而且毁掉本来好的查询
"怎么允许 PVC 扩容?" 表面是 PVC,但 `allowVolumeExpansion` 是 **StorageClass** 的字段。
关键词路由误判到 PVC → **硬过滤把正确答案删没** → 一个**本来能答对**的查询被"优化"搞坏了。
**没有 eval,你会自信地上线一个净负优化。**

### 3. 硬过滤 → 软加权:把"删除"换成"加分"
硬过滤误路由=灾难(答案消失)。改成**软加权**(命中资源 +0.05 分,谁都不删):
- 路由对 → 享受加分
- 路由错 → 答案只是排名略降,**永不消失**
结果:③ auto 不再低于 ① 基线(消除净负),代价是召回上限不如硬过滤。**这是"安全 vs 上限"的权衡,boost 是可调旋钮。**

### 4. rerank 是这一路的赢家,且 roadmap 顺序 ≠ 价值顺序
④ rerank(向量粗召回 top-10 → cross-encoder 精排)**唯一把两个指标都打满**:
- 救起卡死的多 chunk "必填字段"(recall 1/2 → **2/2**):cross-encoder 读懂"provisioner **必填**"对"**必填**字段"的强相关,这是余弦看不出的。
- 修了"PVC扩容"排序(rank 2→1)**哪怕路由判错**——rerank 不管路由,直接读真实相关性。

**我们按 ②→③→④ 做,但价值是 ④ >> ②/路由。教训:测量不只决定"做不做",还决定"先做哪个"。**

## 它们如何组合(规模化时)

- **现在 22 段**:rerank 全量即可,路由冗余。
- **⑤ 几万段时**:rerank 每条候选都算、贵 → **先用路由/过滤把候选从几万砍到几百(便宜)→ 再 rerank 精排(贵但少)**。
- 所以 ②/路由不是白做,它会从"质量手段"变成"成本手段"。**它们是组合,不是二选一。**

## 一个天花板要记住

**rerank 只能重排粗召回捞到的东西。** 正确 chunk 没进 `COARSE_N`,精排也救不回 → 那是调大粗召回的信号,不是 rerank 不行。
